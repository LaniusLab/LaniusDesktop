# ADR-0010：作业资产为「按键方案 + 预设操作」的有序模板，在选定窗口句柄上执行

- 状态：已接受
- 日期：2026-09-18

## 背景

M0 把作业建成通用 DAG：`nodes[]` + `control` 边，编排页是 React Flow 画布，目标窗口写在图中间的 `window.find` 节点里。实际使用方式是：先定制按键方案（宏表），再把【按键 / 鼠标】和预设操作拖进一套模板，运行时选进程、把模板打到该窗口句柄上。图模型把「对谁执行」和「做什么」缠在一起，连线成本高，也不支持选进程时推荐并改定位通道（控件树 / 画面）。

## 决策

1. **资产是有序模板，不是自由 DAG。** `*.flow.json` 的真源步骤是 `steps[]`。步骤三种 `kind`：`binding`（按键方案里的一条）、`mouse`（鼠标预设）、`preset`（引擎注册的操作，如等待、日志、识图等待）。控制结构（条件 / 循环）以后作为可嵌套的 preset，不恢复任意连线。
2. **目标窗口是执行绑定，不是步骤。** 模板带 `target.match`（exe / 标题 / 类名，禁止持久化 pid）与 `target.locate`（通道、截图后端、识图包）。开跑时列出进程，引擎按窗口特征推荐 locate，用户可改；当次覆盖走 `flow.start.inputs`。
3. **按键方案仍是本机宏表。** 流程只存 `keymapProfileId` + 步骤上的 `profileId` / `mappingId`，并冗余 `keys` 供引擎执行（引擎不读 UI 的 localStorage）。
4. **编排是拖拽序列。** 左侧调色板（方案映射表、鼠标、预设操作）拖到右侧步骤列表；点选亦可追加。不再用节点画布作为主编辑器。
5. **schemaVersion 2。** v1 的 `nodes`/`edges` 经单向迁移变成 `kind: preset` 的步骤序列。

## 理由

- 与「对指定 hwnd 重放键鼠 + 可选识图」的产品路径同构；MaaEnd 式「先绑控制器/窗口再跑任务」可映射为 target 绑定，而不引入第二套 Pipeline JSON。
- 有序列表可拖拽、可审计、可 diff；办公白盒与黑盒画面作业共用同一模板形状，只换 `locate.channel` 与 preset 集合。
- 键鼠全局互斥、协作式取消、dry-run ≡ mock driver 等执行语义不变，只换调度输入从拓扑图变成序列。

## 后果

- 编排页不再依赖 React Flow；`@xyflow/react` 移出运行时依赖。ADR-0002（前端用 React）仍然成立，画布生态不再是选型理由。
- `window.find` 不再作为普通步骤的默认形态；找窗发生在开跑绑定。多窗口作业用 `target` 默认句柄，步骤级覆盖属后续。
- 通道切换不自动改写步骤类型：画面作业缺控件定位器时，把 locate 改成 `a11y` 必须警告。积木双绑定（同一人话步骤同时带选择器与模板图）属后续。
- 识图 preset（`vision.*`）与真进程枚举仍按里程碑落地；M0 用 mock 进程列表 + 推荐通道，引擎 mock driver 记录 `find_window` / `press` / `click`。

## 备选（已否决）

- **保留 DAG，只把 keymap 当积木：** 目标窗口与顺序仍分散在边上，拖拽键鼠不自然。
- **接入 MaaFramework Pipeline：** 第二运行时、第二份 JSON 协议，违反 Python sidecar 与 schema 真源。
- **运行时把 `element.*` 静默映射成找图：** 无模板、误点击，违反「失败要响亮」。
